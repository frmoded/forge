# v0.2.73 — Investigation: slot-resolution second pass writes stale `# Python`

**Driver-reported failure**: at v0.2.72, the Step-5 smoke (edit slot text → re-run) writes the new `english_hash` to frontmatter but does NOT replace the stale `# Python` body. User sees the original storybook greeting in the output panel; on disk, `english_hash` is Victorian but `# Python` is still storybook.

## Findings

Three hypotheses tested. Two refuted, one confirmed.

### Hypothesis A — `writePythonAndEnglishHash` body-merge defect

**REFUTED.** Pure-core unit tests in `forge-client-obsidian/src/python-cache-writer-stale-write-investigation.test.ts` exercise the exact body shape from the smoke (frontmatter with stale `english_hash`, Victorian English, storybook `# Python`) and assert that calling `writePythonAndEnglishHash` with new Python + new hash correctly replaces BOTH. All 3 assertions pass against v0.2.72 code:

- The stale `english_hash` is replaced with the new value.
- The stale `# Python` block is replaced with the new code.
- Only one `# Python` heading remains (no duplicate).

The plugin-side body-merge logic is innocent.

### Hypothesis B — Engine returns OLD code on second pass despite `slot_resolutions`

**REFUTED.** Pytest tests in `forge/tests/core/test_executor_stale_python_investigation.py` exercise `resolve_action_code(snip, slot_resolutions={...})` on the exact post-Step-5 state with `facet_form: canonical` present. All 3 cases pass:

- Stale `# Python` + stale `english_hash` + Victorian `# English` + `slot_resolutions={Victorian: expr}` → engine correctly detects hash mismatch, re-transpiles, returns Victorian Python.
- Cache-hit path: matching `english_hash` → engine returns cached `# Python` (correct).
- Pessimistic `slot_resolutions` on a cache-hit case: engine returns cached `# Python` (correct).

The engine's canonical-path branch handles `slot_resolutions` correctly when `facet_form` is present.

### Hypothesis C — `facet_form: canonical` dropped from frontmatter

**CONFIRMED.** Pytest case `test_hypothesis_c_engine_returns_stale_python_when_facet_form_absent` constructs the user's failing state with `facet_form` ABSENT from the snippet's `meta` dict (simulating Obsidian's YAML serializer stripping the field on save). Engine returns the STALE storybook `# Python` regardless of:

- The english_hash mismatch (stored storybook hash vs current Victorian English).
- The `slot_resolutions` dict being explicitly provided.

This matches the user's observation precisely:

| Observed | Mechanism |
| --- | --- |
| `english_hash` updates to Victorian on disk | Plugin reads fresh body, computes Victorian hash, writes via `writePythonAndEnglishHash` (innocent). |
| `# Python` does NOT update (still storybook) | Engine returns storybook code as `_forge_compute_with_python`'s third tuple element because `facet_form != "canonical"` triggers the legacy early-return at `executor.py:511`. Plugin writes storybook → storybook (no visible change). |

## Root cause

At `forge/forge/core/executor.py:500-512`:

```python
if code is not None:
    if facet_form == "canonical" and edit_mode != "python":
      ...
      if stored_hash == current_hash:
        return code
      # Hash mismatch: fall through to re-transpile.
    else:
      return code   # ← Branch (X)
```

Branch (X) returns the cached `# Python` whenever:
- A `# Python` heading exists, AND
- `facet_form != "canonical"` (could be missing, malformed, or set to a non-canonical value).

This is correct for legacy free-English snippets (no facet_form, just a pre-generated Python facet). It is INCORRECT when the plugin has explicitly provided `slot_resolutions` — the plugin's presence of slot_resolutions signals "the second-pass of a cache-miss round-trip is in progress; please re-transpile with these resolutions and return the new Python."

## Why does `facet_form` go missing?

Two plausible mechanisms; either is consistent with the user's smoke:

1. **Obsidian YAML serializer drops unknown fields.** Obsidian's frontmatter editor parses YAML, presents recognized fields in a UI, and re-serializes on save. Unrecognized fields (anything not in Obsidian's known-tag list) MAY be preserved, MAY be dropped depending on plugin install state, MAY be reordered. `facet_form: canonical` is a Forge-specific field; Obsidian doesn't know it.

2. **The plugin's own write inadvertently strips the field.** Less likely: `writePythonAndEnglishHash` does line-level replacement of `english_hash:` and the `# Python` block. It doesn't touch other frontmatter lines per the helper's tests. But a previous code path (e.g., `_extractEnglishFromBody`) could be rewriting the body. (Auditing this is part of the fix prompt's diligence.)

Either way, the engine should be robust to this — `slot_resolutions` presence should ALWAYS force re-transpile.

## Fix design

`resolve_action_code(snippet, slot_resolutions=None)` change:

```python
if code is not None:
    # v0.2.73: if slot_resolutions is explicitly provided, the plugin
    # is in the second-pass of a cache-miss round-trip. Skip the
    # cached-# Python early-return path; re-transpile with the
    # provided resolutions and return the new Python. The plugin
    # writes that back to # Python as part of handleSlotCacheMiss.
    if slot_resolutions is not None:
      pass  # fall through to transpile
    elif facet_form == "canonical" and edit_mode != "python":
      ...  # english_hash check as before
    else:
      return code  # legacy path
```

This makes the engine respect the plugin's intent: "you're calling me with resolutions, so I should use them."
