### §B — The "body=119ch" smoking gun

The driver's debug log says `body=119ch` but the on-disk body is
**308 chars** (`# English` + storybook + `# Python` heading + python
code block). Where does 119 come from?

```
$ wc -c /Users/odedfuhrmann/projects/forge-moda/slot_demo.md
     415 /Users/odedfuhrmann/projects/forge-moda/slot_demo.md

$ .venv/bin/python3 -c "
from forge.core.snippet_registry import parse_frontmatter
with open('/Users/odedfuhrmann/projects/forge-moda/slot_demo.md') as f:
    content = f.read()
meta, body = parse_frontmatter(content)
print('Bundled body len:', len(body))
print('Bundled meta english_hash:', repr(meta.get('english_hash')))
print('First 80 chars:', repr(body[:80]))
"
Bundled body len: 119
Bundled meta english_hash: None
First 80 chars: '# English\n\nSet greeting to {{a friendly hello message in the style of a children'
```

**The bundled `forge-moda/slot_demo.md` body is exactly 119 chars
with no `# Python` heading and no `english_hash` frontmatter.**

The engine is reading the BUNDLED body — i.e., the body the
SnippetRegistry cached at install/scan time — NOT the user's edited
on-disk body. The cache lookup `_vaults['forge-moda']['slot_demo']`
returns the stale-since-install entry: `{english_hash=None,
body=119ch}`. Computed hash on that body = `f44f75cf…` (same English
text), stored hash = None → `f44f75cf != None` → cache miss every
click.

The engine NEVER sees the disk's `english_hash` or the disk's
`# Python`. Disk and registry have diverged irreversibly.

### §C — Hypothesis A confirmed: `refresh_file` writes to the wrong vault

`SnippetRegistry.refresh_file` at `forge/core/snippet_registry.py:78`:

```python
def refresh_file(self, filepath: str,
                 vault_name: str = AUTHORING_VAULT,
                 source: str = "authoring") -> Optional[str]:
    vault_path = None
    if vault_name in self._vaults:
      for entry in self._vaults[vault_name].values():
        vault_path = entry.get("vault_path")
        if vault_path:
          break
    if not vault_path:
      vault_path = os.path.dirname(filepath)
    self._vaults.setdefault(vault_name, {})
    return self._index_authoring_file(filepath, vault_name, source, vault_path)
```

Defaults `vault_name=AUTHORING_VAULT` regardless of filepath. The
plugin's `_forge_sync_user_file` (pyodide-host.ts line ~604) calls
this with NO `vault_name` argument:

```ts
self.snippet_registry.refresh_file(p)  # ← vault_name unspecified
```

So for `/Users/odedfuhrmann/forge-vaults/bluh/forge-moda/slot_demo.md`
the call writes the fresh entry into `_vaults[AUTHORING]['slot_demo']`
(keyed by basename, per `_index_authoring_file:242`). The library
entry at `_vaults['forge-moda']['slot_demo']` is NEVER touched after
the initial `_scan_library_vault` ran.

When the next Forge-click looks up the qualified id
`forge-moda/slot_demo`, `get()` at line 147-149 routes DIRECT to
`_vaults['forge-moda']['slot_demo']` — the stale, no-`# Python`,
no-`english_hash` entry from install time.

### §E — Why B / C / D / E are refuted

- **Hypothesis B (MEMFS != disk)**: refuted indirectly. The bug
  reproduces in plain Python (no MEMFS layer at all) — the
  reproduction test uses a plain temporary directory. MEMFS sync
  is irrelevant when the registry itself is the staleness layer.
- **Hypothesis C (extraction divergence)**: refuted by §A —
  both helpers produce `f44f75cf…` on the user's on-disk bytes.
- **Hypothesis D (frontmatter parse divergence)**: refuted by §A —
  `parse_frontmatter` returns `english_hash=f44f75cf…` exactly.
- **Hypothesis E (plugin write-side body-read race)**: refuted by §B —
  the engine doesn't even SEE the on-disk body, so any race in the
  plugin's write-side body-read can't matter for the cache-miss
  symptom. The persisted `english_hash` on disk is provably correct
  (matches the disk English content); the bug is on the read side
  inside the engine's registry.

### §F — Phase 2 fix (designed; implementation follows)

`refresh_file` MUST detect which vault the filepath belongs to,
NOT default to `AUTHORING_VAULT`. The detection rule: find the vault
whose `vault_path` is the **longest matching prefix** of `filepath`.
That uniquely identifies the right vault for any file in the
authoring vault root, in a library subdirectory, in a builtin
(though builtins are never refreshed from disk), and even in nested
authoring subdirs.

Once the vault is identified, the bare_id computation must match
that vault's storage convention:
- library vaults: `os.path.relpath(filepath, vault_path)` with
  extension stripped and separators normalized (per
  `_scan_library_vault:208-209`).
- authoring vaults: `os.path.splitext(os.path.basename(filepath))[0]`
  (per `_index_authoring_file:242`).

Fall back to current authoring-vault behavior only when no vault
matches (e.g., refresh on a file that exists nowhere in the registry
— possible for a brand-new authoring file written before any scan
indexed it).
