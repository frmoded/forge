# v0.2.74 — Investigation: `english_hash` parity break on real fixtures

## Hypothesis (from prompt §0)

The cowork-reported bug: cache never hits because the plugin's TS
`computeEnglishHash` and engine's Python `compute_english_hash`
disagree on the bundled `slot_demo.md` English content. The
v0.2.72 cross-language pin used a SHORT input
(`"Set greeting to {{a friendly hello}}.\nDo [[print]](greeting)."`)
which happened to normalize identically; the longer real-fixture
slot text was hypothesized to expose divergence.

## Method

1. Read the EXACT current `~/projects/forge-moda/slot_demo.md`
   English facet via Python `extract_section` and TS
   `_extractEnglishFromBody`.
2. Dump the UTF-8 hex bytes of each.
3. Compute both helpers' sha256 over the extracted English.
4. Also test multiple input shapes (varied whitespace, paragraph
   breaks, unicode).

### What `5fe21a3d…` actually is

Cross-check against the Victorian text mentioned in the v0.2.73
feedback:

```
Victorian input:    "Set greeting to {{a formal hello message in the style of a Victorian letter}}.\nDo [[print]](greeting)."
Python hash:        5fe21a3d85ff8df536854a08a8c22556b249a236858f2d7d5737b98b4b6ccada
```

The on-disk `english_hash: 5fe21a3d…` the cowork observed is the
**correct hash for the Victorian English text**, not a divergent
result for the storybook text.

### Conclusion: hypothesis REFUTED

Per cc-prompt-queue.md §76 — "If the failing test passes against
current code, the bug isn't where the prompt hypothesized."

The user's vault appears to have `english_hash: 5fe21a3d…` (Victorian)
persisted with `# English` reverted to storybook. The cache mismatch
the cowork observed is real, but the cause is NOT a TS↔Python parity
break.

## Plausible actual causes (route to questions/ for user
disambiguation)

1. **User edited English to Victorian during a prior Forge-click
   session, then reverted manually (git checkout, manual edit,
   undo, etc.) without re-running Forge.** The `english_hash`
   stayed at the Victorian value because no compute fired to
   refresh it after the revert.

2. **Plugin's write-side bug where the body passed to
   `writePythonAndEnglishHash` and the body used to compute
   `englishHash` differ.** The current main.ts handleSlotCacheMiss
   reads the body TWICE — once via `vault.read(file)` for hashing,
   once again inside `vault.process(file, fn)` for the write
   transform. If the body changes between those two reads
   (vault.on('modify') firing async during /resolve-slot's network
   round-trip), the persisted `english_hash` could match the FIRST
   body while the in-disk `# English` matches the SECOND.

3. **Auto re-extract on plugin upgrade overwrote `# English`
   without resetting `english_hash` in frontmatter.** The bundled
   fixture has no `english_hash` field; if re-extract copies the
   bundled file's content but the per-vault frontmatter survives
   somehow, this could explain the inconsistency.
